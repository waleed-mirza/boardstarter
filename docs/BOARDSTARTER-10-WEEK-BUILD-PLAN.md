# Boardstarter — 10-Week Build Plan (Agent Edition)

**Product:** Boardstarter — an open-source, self-hostable niche job board template (MIT).
**Stack:** Next.js 16 · Supabase · Netlify · Lemon Squeezy.
**Outcome after Week 10:** a public MIT repo, a live demo, and docs so someone can go from clone to a running board in under 15 minutes.
**Distribution:** this repository is free to use, modify, and ship under the MIT license.
**Method:** vibe-coded by an AI agent, with tests as the only accepted proof of completion.

## Product identity

| | |
|---|---|
| **Name** | Boardstarter |
| **Tagline** | Launch a paid niche job board this weekend. |
| **Positioning line** | Next.js + Supabase + Netlify. A template you clone, configure, and run yourself. |
| **Repo / package** | `boardstarter` |
| **License** | MIT (`LICENSE`) |
| **Domain** | `boardstarter.dev` preferred (`.dev` is native to this market — supastarter.dev, turbostarter.dev, staarter.dev); `.com` if available |

**Naming rules the agent must follow:**

1. Always pair the name with "job board" in user-facing copy on first mention, so "board" never reads as kanban or board-of-directors. "Boardstarter — the job board template" on first use, plain "Boardstarter" after.
2. The `-starter` suffix is the positioning. It signals a boilerplate you clone and own. Never describe Boardstarter as a "platform", "SaaS", or "service" — it is a template you self-host.
3. **The demo board does not carry the product name.** It gets a real niche identity of its own (e.g. "Next Jobs", "AI Video Jobs") so it functions as a genuine board and an SEO asset rather than an obvious demo. Boardstarter branding appears only on the project site, never on a deployed board's own chrome.
4. Do not use the name in seed data, preset names, or default site settings. A fresh install must show that board's name, never "Boardstarter" — a leaked product name on a deployed site is a Week 9 audit failure.
5. Casing is always `Boardstarter` — one word, capital B only. Not "BoardStarter", "Board Starter", or "boardStarter". A lint rule in CI enforces this in docs and user-facing strings.

*(Name collisions checked and avoided: JobBoardKit, BoardKit, Boardly, JBoard, Niceboard, JobBoard.io, Boardable, Rolekit, JobForge all exist as other products. Verify domain availability at a registrar before Week 10.)*

## 0. How the agent uses this document

Read this section before writing a single line of code.

### 0.1 Operating rules (non-negotiable)

1. **Docs before code.** Next.js 16 differs from most training data. Before touching any Next.js API, read the version-matched docs bundled at `node_modules/next/dist/docs/`. `AGENTS.md` at the repo root points there and is regenerated by `next dev` — never delete its managed block.
2. **Plan, then build.** At the start of every week, output a file-by-file plan (paths, exports, types, test names) and stop. Only after the plan is approved do you write code.
3. **Tests are the definition of done.** A week is complete when its Test Gate passes in CI, not when the feature "works on my machine." Never mark a task complete with a failing, skipped, or deleted test.
4. **Test-first on anything that touches money, auth, or published state.** Webhooks, RLS policies, status transitions, and role checks get their test written before their implementation.
5. **Never disable a test to make the suite green.** If a test fails, the code is wrong until proven otherwise.
6. **Three-strike rule.** If the same bug survives three fix attempts, stop patching. Write the smallest failing reproduction test, then fix against that test.
7. **Run locally, don't mock locally.** Supabase runs on your machine via the CLI. Test against the real database. Mock only third-party HTTP (Lemon Squeezy, Resend, Groq).
8. **One PR per week.** CI green before merge. Tag the merge `week-01` … `week-10` so any week can be rolled back cleanly.
9. **Deploy every week.** Local-green and Netlify-green are different things. A week is not done until the deployed preview passes the smoke suite.
10. **No secrets in the repo.** `.env.example` documents every variable; `.env.local` is git-ignored and never printed into logs or commit messages.

### 0.2 Forbidden patterns (CI greps for these)

| Forbidden | Use instead |
|---|---|
| `middleware.ts` | `proxy.ts` (Next 16 renamed it; runtime is Node, not Edge) |
| Sync `params`, `searchParams`, `cookies()`, `headers()` | `await` them — sync access was removed in Next 16 |
| `@supabase/auth-helpers-nextjs` | `@supabase/ssr` |
| `supabase.auth.getSession()` on the server | `supabase.auth.getUser()` |
| Cookie `get()` / `set()` / `remove()` | `getAll()` / `setAll()` only |
| `revalidateTag('x')` (one arg) | `revalidateTag('x', 'max')` or `updateTag('x')` in a Server Action |
| `SUPABASE_SECRET_KEY` anywhere reachable from a client bundle | server-only module with `import 'server-only'` |
| Supabase queries inside components | a function in `src/lib/data/*` |
| `any`, `@ts-ignore`, `eslint-disable` with no reason comment | fix the type |
| Trusting client-submitted `status`, `price`, `is_featured`, `expires_at` | derive server-side from the package row |
| String-interpolated SQL | parameterized queries / `websearch_to_tsquery` |
| Emoji used as UI icons | Lucide icons |

### 0.3 Per-task loop

```
read AGENTS.md + relevant docs
→ write/extend the test
→ implement the smallest change that passes
→ run: pnpm typecheck && pnpm lint && pnpm test:unit
→ run the layer-specific suite (test:db / test:e2e) if touched
→ commit with a message naming the test that now passes
```

### 0.4 Time budget

8–12 focused hours per week (weekend-shaped: one long session + one short session). If a week overruns, cut scope from the *optional* list at the bottom of that week — never cut the Test Gate.

## 3. Core patterns

These are the load-bearing conventions. Every week applies them; the Week 9 audit verifies them.

### 3.1 Three Supabase clients, three jobs

```ts
// lib/supabase/server.ts — RSCs and Server Actions. RLS applies. This is the default.
// lib/supabase/client.ts — browser components only. RLS applies.
// lib/supabase/admin.ts  — webhook handler, cron routes, and explicit admin mutations.
//                          RLS bypassed. Starts with: import 'server-only'
```

Rule: if you reach for `admin.ts`, write a one-line comment saying why RLS could not do the job. Any use outside `api/webhooks/*`, `api/cron/*`, `lib/actions/admin/*`, and `scripts/*` is a bug.

### 3.2 Data layer, not queries-in-components

```ts
// lib/data/jobs.ts
export async function listPublishedJobs(filters: JobFilters, page: number): Promise<Paginated<JobListItem>>
export async function getJobBySlug(slug: string): Promise<JobDetail | null>
export async function getEmployerJobs(companyId: string): Promise<EmployerJob[]>
```

Components call these. Nothing else calls Supabase. This is what makes the filter logic unit-testable and the app portable if an operator swaps the database.

### 3.3 Server Action shape

Every action follows the same five steps, in order:

```ts
'use server'
export async function postJob(input: unknown): Promise<ActionResult<{ jobId: string }>> {
  const user = await requireRole('employer')          // 1. authorize
  const data = jobSchema.parse(input)                 // 2. validate (Zod)
  const job  = await jobs.createDraft(user, data)     // 3. delegate to the data layer
  updateTag(`company-${user.companyId}`)              // 4. invalidate (read-your-writes)
  return ok({ jobId: job.id })                        // 5. typed result, never a raw throw
}
```

`ActionResult<T>` is a discriminated union: `{ ok: true, data: T } | { ok: false, error: string, field?: string }`. Forms render `error` inline. Nothing leaks a stack trace to the client.

### 3.4 RLS is the security boundary

Action-level checks are user experience. Row Level Security is enforcement. Every table has RLS enabled and a pgTAP test proving both the positive and the negative case. A new table without an RLS policy fails `scripts/verify-security.ts` in CI.

Employers can never write `status`, `is_featured`, `published_at`, or `expires_at`. A `BEFORE UPDATE` trigger rejects changes to those columns unless the caller is the secret-key role. The webhook is the only path that publishes a job.

### 3.5 Payment provider adapter

```ts
export interface PaymentProvider {
  createCheckout(i: { jobId: string; packageId: string; email: string }): Promise<{ url: string }>
  parseWebhook(req: Request): Promise<WebhookEvent>   // verifies signature, normalizes shape
}
export type WebhookEvent =
  | { type: 'order_paid';           jobId: string; orderId: string; amountCents: number; currency: string; raw: unknown }
  | { type: 'order_refunded';       orderId: string; raw: unknown }
  | { type: 'subscription_changed'; companyId: string; activeUntil: string | null; raw: unknown }
  | { type: 'ignore' }
```

The route handler contains zero Lemon Squeezy specifics. `fake.ts` implements the same interface and drives a contract test suite — if the fake passes every flow, a future Polar/Dodo/Stripe-Managed-Payments adapter will too.

### 3.6 Caching

Tag-based, explicit. `cacheTag('jobs')` on list queries, `cacheTag('job-'+id)` on details. Publishing calls `updateTag('jobs')` for read-your-writes; background changes use `revalidateTag('jobs', 'max')` — the two-argument form, since the single-argument form is deprecated in Next 16.

### 3.7 Configuration over code

Anything an operator might change lives in the `site_settings` table or a preset file, never hardcoded: site name, tagline, accent color, apply modes, auto-publish on payment, alert frequency, footer links, analytics snippet. Changing a setting must not require a redeploy.

## 4. Testing system

The spine of the project. Five layers, each with a different job.

| Layer | Tool | Scope | Command | Runs |
|---|---|---|---|---|
| L1 Database | pgTAP | schema shape, constraints, triggers, **every RLS policy** | `pnpm test:db` | CI + pre-merge |
| L2 Unit | Vitest | pure logic: validation, filter→query mapping, webhook parsing, JSON-LD builders, date/money math, slugs | `pnpm test:unit` | on every save |
| L3 Integration | Vitest | server actions + data layer against local Supabase | `pnpm test:int` | CI + pre-merge |
| L4 E2E | Playwright | user journeys against a production build + local Supabase | `pnpm test:e2e` | CI + pre-merge |
| L5 Smoke | Playwright (subset, tagged `@smoke`) | the deployed Netlify preview URL | `pnpm test:smoke -- --url=…` | after every deploy |

Plus two cross-cutting checks that run inside L4:

- **Accessibility:** `@axe-core/playwright` on home, job list, job detail, post-job form, dashboard, admin queue. Zero serious or critical violations, every week.
- **Visual regression:** `toHaveScreenshot` on the same six surfaces, light and dark, desktop and mobile. Baselines committed. A diff is a failure until a human approves the new baseline.

### 4.1 Coverage gates

| Path | Minimum line coverage |
|---|---|
| `lib/payments/**` | 95% |
| `lib/validation/**` | 95% |
| `lib/data/**` | 90% |
| `lib/seo/**` | 90% |
| `lib/auth/**` | 90% |
| everything else | 70% |

CI fails below these numbers. Coverage is a floor, not a goal — a 100%-covered webhook with no replay test is still broken.

### 4.2 Test naming

```
describe('<unit under test>', () => {
  it('<does X> when <condition>', …)
  it('rejects <bad input> with <specific error>', …)
})
```

Every bug found manually gets a regression test named after the bug before it is fixed.

### 4.3 The weekly gate rule

Each week below ends with a **Test Gate**: a numbered list of assertions. All must pass in CI, plus the deployed smoke run, before the next week begins. No partial credit, no "I'll come back to it."

## 5. UI/UX system

The template is judged on screenshots before anyone reads a line of its code. The design system is a product feature, not decoration. It is defined once, in Week 1, and every later week conforms to it.

### 5.1 Design direction

**Reference quality bar:** Linear, Vercel dashboard, Resend, WorkOS, Cal.com. Restrained, dense, border-driven, monochrome with one accent. **Content references for the board itself:** the scan-ability of a well-run job list — a row you can read in one second, not a card grid that fits six jobs per screen.

Three principles, applied everywhere:

1. **Borders, not shadows.** Structure comes from 1px hairlines and background steps. Shadows appear only on things that genuinely float: dropdowns, popovers, dialogs, toasts.
2. **Density with air.** A job board is a list product. Rows are compact (72px desktop) and scannable; breathing room comes from generous section padding, not from bloating each row.
3. **One accent, used sparingly.** The accent color appears on primary buttons, active states, focus rings, and the "Featured" marker. Nowhere else. Everything else is neutral.

### 5.2 Anti-slop rules (an automatic reject list)

These are the tells that make a template look AI-generated. None of them ship.

| Never | Instead |
|---|---|
| Purple→blue (or any) gradient hero | Flat background, one strong headline, real screenshot |
| Glassmorphism, backdrop blur cards, neon glows | Solid surfaces, 1px borders |
| Emoji as icons or in headings (🚀 ✨ 💼) | Lucide icons at 16/20px |
| Gradient text, animated gradient borders | Solid `--fg`, weight and size for emphasis |
| Three font families, six font weights | One family, weights 400/500/600 only |
| Card grid for job listings | Dense list rows; cards only for the featured strip |
| Rainbow-colored category badges | One muted badge style; color only for status semantics |
| Everything center-aligned | Left-aligned text; center only for empty states and auth cards |
| Mixed corner radii (4px here, 16px there) | One radius scale derived from a single `--radius` |
| Drop shadow on every card and button | See principle 1 |
| Decorative stock photos of people in offices | Company logos, real content, generous whitespace |
| Fake charts with invented data on a dashboard | Real counters from the database, or no chart |
| "✨ AI-Powered ✨", "Supercharge", "Revolutionize" copy | Plain nouns and verbs: "Post a job", "12 jobs live" |
| Full-width paragraphs spanning 1400px | `max-w-[68ch]` on prose |
| Entrance animations on page load, parallax, scroll-jacking | Motion only on interaction, 120–200ms |
| Placeholder lorem ipsum in the demo | 40–60 realistic seeded jobs |

### 5.3 Tokens (Tailwind v4 `@theme`, in `src/styles/globals.css`)

Define semantic tokens in OKLCH. Components reference tokens, never raw color values.

```css
@theme {
  /* Neutrals — the whole UI is built from these */
  --color-bg:           oklch(100% 0 0);
  --color-bg-subtle:    oklch(98.4% 0.002 250);
  --color-bg-muted:     oklch(96.5% 0.003 250);
  --color-border:       oklch(92.5% 0.004 250);
  --color-border-strong:oklch(87% 0.005 250);
  --color-fg:           oklch(21% 0.006 250);
  --color-fg-muted:     oklch(50% 0.008 250);
  --color-fg-subtle:    oklch(64% 0.007 250);

  /* Accent — the ONE color; swapped per preset */
  --color-accent:       oklch(55% 0.17 255);
  --color-accent-fg:    oklch(99% 0 0);
  --color-accent-subtle:oklch(96% 0.03 255);

  /* Status — semantic only, never decorative */
  --color-success:      oklch(58% 0.13 155);
  --color-warning:      oklch(70% 0.15 75);
  --color-danger:       oklch(58% 0.19 25);

  /* Radius — one source */
  --radius: 0.5rem;              /* sm .375 · md .5 · lg .75 · full 9999 */

  /* Type scale — 8 sizes, no improvisation */
  --text-2xs: .6875rem;  /* 11 — table meta, uppercase labels */
  --text-xs:  .75rem;    /* 12 — badges, timestamps */
  --text-sm:  .875rem;   /* 14 — UI default, table body */
  --text-base:1rem;      /* 16 — prose */
  --text-lg:  1.125rem;  /* 18 — job titles in rows */
  --text-xl:  1.375rem;  /* 22 — section headings */
  --text-2xl: 1.75rem;   /* 28 — page titles */
  --text-3xl: 2.5rem;    /* 40 — marketing h1 only */
}
```

Dark mode redefines only these tokens under `.dark`. No component contains a `dark:` color literal beyond what a token cannot express.

**Spacing:** 4px base. Allowed steps: 4, 8, 12, 16, 24, 32, 48, 64, 96. Nothing else.
**Type rules:** headings ≥ 28px get `letter-spacing: -0.02em`. Body line-height 1.55, headings 1.2. Numbers in tables use `font-variant-numeric: tabular-nums`.
**Focus:** every interactive element shows a 2px accent ring with 2px offset. Never `outline: none` without a replacement.
**Motion:** 120ms for hover/press, 200ms for panels and sheets, `ease-out`. Respect `prefers-reduced-motion` globally.

### 5.4 Component inventory

Built from shadcn/ui primitives, copied in and restyled to the tokens above. Week 1 delivers the primitives; later weeks compose them.

**Primitives (Week 1):** Button (primary/secondary/ghost/destructive · sm/md/lg), Input, Textarea, Select, Combobox, Checkbox, RadioGroup, Switch, Label, Badge, Avatar, Separator, Card, Tabs, Dialog, Sheet, DropdownMenu, Popover, Tooltip, Toast (Sonner), Skeleton, Pagination, Table.

**Patterns (Week 1, filled in later):**
- `PageHeader` — title, description, actions slot. Used on every dashboard and admin page so they never drift apart.
- `EmptyState` — icon, one-line explanation, primary action. Every list has one. No blank screens, ever.
- `DataTable` — sortable headers, row actions, sticky header, mobile card fallback.
- `StatusPill` — draft / pending / live / expired / rejected, each with a fixed color and label.

## Week 6 — Payments (the highest-risk week)

**Goal:** money moves, jobs go live, and nothing double-charges, double-publishes, or trusts the client. Test-first throughout.

### Tasks

1. Define `PaymentProvider` and `WebhookEvent` (§3.5). Write the **contract test suite** against `fake.ts` before implementing Lemon Squeezy.
2. Lemon Squeezy setup: store, product, three variants matching the seeded packages, webhook endpoint, signing secret.
3. `createCheckout`: `POST /v1/checkouts` with the variant ID, `checkout_data.custom.job_id`, `checkout_data.email`, and a redirect URL back to the dashboard. Price and duration come from the `packages` row — never from the request.
4. Webhook route: read the **raw body text**, verify `X-Signature` with HMAC-SHA256 and `crypto.timingSafeEqual`, then dispatch on `meta.event_name` and read `meta.custom_data`.
5. Publish transition inside a transaction, using the admin client: insert the order, set `published_at`, `expires_at = now() + package.duration_days`, `is_featured` from the package, and `status` to `published` (or `pending_review` when auto-publish is off).
6. Idempotency: unique constraint on `orders.provider_order_id`; a duplicate delivery is a no-op that still returns 200.
7. Handle `order_refunded` → job expired, order marked refunded.
8. Renew: a new checkout for an existing job; `expires_at` extends from `max(now(), current expires_at)`.
9. Package selection UI (three radio cards per §5.5), a checkout loading state, a post-payment success page, and a "payment received, publishing…" state for the webhook race.
10. Structured logging of every webhook: event, order ID, job ID, result. No secrets in logs.
11. Fixtures: capture real Lemon Squeezy test-mode payloads into `tests/fixtures/webhooks/`.

### Test Gate 6

**Signature verification**
1. A correctly signed payload is accepted.
2. A tampered body with the original signature is rejected with 400.
3. A signature computed with the wrong secret is rejected.
4. A missing `X-Signature` header is rejected.
5. A malformed hex signature is rejected without throwing.
6. Comparison uses `timingSafeEqual` (asserted by code inspection test or by a lint rule).

**Event handling**
7. `order_created` publishes the job with the correct `expires_at`, `is_featured`, and order row.
8. `order_refunded` expires the job and marks the order refunded.
9. An unknown event name returns 200 and changes nothing.
10. Missing `meta.custom_data.job_id` returns 400, logs, and does not crash.
11. A `job_id` that does not exist returns 400 and creates no order.
12. A payload whose amount does not match the package price is recorded and flagged, not silently accepted.

**Idempotency and ordering**
13. The same `order_created` delivered twice creates one order row and publishes once.
14. Ten concurrent identical deliveries produce exactly one order row.
15. A refund arriving before its order is handled without corrupting state.
16. A webhook for an already-published job does not extend `expires_at` twice.

**Authorization and integrity**
17. `createCheckout` for another employer's job is rejected.
18. Price and duration are read from the database; a request with a tampered price is ignored.
19. No path publishes a job without a corresponding paid order row (assert by attempting every action as an employer, then querying).

**Adapter contract**
20. The full purchase, refund, and renew flows pass against `fake.ts`, proving provider swappability.

**End to end**
21. E2E with Lemon Squeezy test mode: post → select package → checkout → webhook → job live on the public board.
22. E2E: renew extends the expiry correctly from both a live and an expired state.
23. E2E: double-clicking submit does not create two checkouts.
24. Coverage: `lib/payments` ≥ 95%.

**Done when:** all 24 pass and the money path has no untested branch. This week does not get shortened.

## Appendix D — Failure modes to watch for

Recurring ways an AI agent breaks this specific stack. Check for these during review.

1. Writing Next 15 patterns from training data — sync `params`, `middleware.ts`, one-argument `revalidateTag`.
2. Reaching for `@supabase/auth-helpers-nextjs`.
3. Using `getSession()` server-side, or individual cookie methods.
4. Importing the admin client into something a client component can reach.
5. Trusting client-supplied `status`, `price`, or `expires_at`.
6. Shipping a webhook with no idempotency key.
7. Creating a table and forgetting to enable RLS.
8. Writing a policy test that only checks the positive case.
9. Seeding with hardcoded UUIDs that collide on re-seed.
10. "Fixing" a failing test by changing its assertion.
11. Adding a color, radius, or spacing value outside the token set.
12. Adding a shadow to a non-floating element.
13. Building a card grid because it is easier than a well-aligned dense row.
14. Leaving a list without an empty state.
15. Building the light theme and treating dark mode as a find-and-replace.
